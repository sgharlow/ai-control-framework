# The Context Preservation Protocol: How I Stopped AI Sessions From Contradicting Each Other

**Subtitle:** End the chaos of inconsistent AI-generated code across sessions.

---

## The Hidden Problem

You've been using AI to build your application for weeks. Everything seems fine. Then one day you notice something strange.

The user service uses `getUserById(userId)`. But the order service uses `getOrder(id)`. The payment service uses `fetchPayment(paymentId)`. Three services. Three different naming conventions. All generated by AI in different sessions.

Worse, you find code that directly queries the database—even though you established a repository pattern in week one. The AI forgot. It made different decisions in different sessions because it had no memory of what came before.

This is context drift. And it's silently destroying your codebase.

---

## What Context Drift Looks Like

Session 1: You establish patterns.

```javascript
// AI creates clean, consistent code
class UserService {
  async getUserById(userId) {
    return this.userRepository.findById(userId);
  }
}
```

Session 2: AI forgets those patterns.

```javascript
// Different naming, different patterns
class OrderService {
  async getOrder(id) {
    return this.orderRepo.find(id); // Different variable name
  }
}
```

Session 3: AI ignores patterns entirely.

```javascript
// Direct database access (repository pattern forgotten)
const fetchUser = (id) => {
  return database.query(`SELECT * FROM users WHERE id = ${id}`);
};
```

Three sessions. Three contradictory implementations. And your codebase is now an archaeological dig of competing styles.

---

## Why Traditional Solutions Fail

**"I'll just remind the AI"**

You can include instructions in every prompt: "Use repository pattern. Follow naming conventions." But instructions get long. You forget things. The AI processes thousands of tokens and sometimes misses what matters.

**"I'll keep session history"**

Session history helps within a session. Between sessions? Gone. Next Tuesday you're starting fresh.

**"I'll use a style guide"**

Style guides are great—if the AI reads them, remembers them, and applies them consistently. Three big assumptions.

The problem isn't capability. It's *systematic context tracking*.

---

## The Context Preservation Protocol

Context preservation is a system for maintaining consistency across AI coding sessions. It tracks what decisions you've made, what patterns you're using, and what conventions you've established—then makes this information available to every future session.

**Four components:**

1. **Architectural Decision Records (ADRs)** - Major decisions and their rationale
2. **Naming Convention Registry** - How things should be named
3. **Pattern Consistency Tracking** - Design patterns in use
4. **Cross-Session State** - What was built and what's next

---

## Component 1: Architectural Decision Records

An ADR captures a significant technical decision. Not every decision—significant ones that affect multiple components.

**When to create an ADR:**
- Choosing a database (PostgreSQL vs MongoDB)
- Adopting a pattern (repository, factory, observer)
- Selecting an authentication approach (JWT vs sessions)
- Deciding on an API style (REST vs GraphQL)

**ADR Format:**

```markdown
# ADR-001: Use Repository Pattern for Data Access

## Status
Accepted

## Context
We need consistent data access across entities while maintaining testability.

## Decision
All data access uses repositories. No direct database queries outside repositories.

## Consequences
- Consistent patterns everywhere
- Easy testing with mock repositories
- Additional abstraction layer

## Implementation
- Every entity has a repository
- Repositories implement shared interface
- Direct DB access prohibited
```

This becomes a reference that any AI session can load. When starting work, the AI reads ADRs and knows: "Repository pattern. No direct queries."

---

## Component 2: Naming Convention Registry

Document how things should be named. Not as prose—as structured data the AI can parse.

```yaml
naming_conventions:
  classes:
    pattern: "PascalCase"
    suffix_by_type:
      service: "Service"
      repository: "Repository"
      controller: "Controller"

  functions:
    pattern: "camelCase"
    prefix_by_action:
      read: ["get", "fetch", "retrieve"]
      create: ["create", "add"]
      update: ["update", "modify"]
      delete: ["delete", "remove"]

  files:
    pattern: "kebab-case"
    suffix_by_type:
      service: ".service.js"
      test: ".test.js"
```

When AI creates a new service, it checks the registry. User service? `UserService`. File name? `user.service.js`. Method to get a user? `getUserById`.

No drift. No conflicting styles.

---

## Component 3: Pattern Consistency Tracking

Track which patterns you're using and how they're implemented.

```yaml
established_patterns:
  data_access:
    pattern: "Repository Pattern"
    implementation: "Interface + Concrete class"
    example: "UserRepository implements IUserRepository"

  error_handling:
    pattern: "Custom Error Classes"
    implementation: "Extend base AppError"
    example: "ValidationError extends AppError"

  validation:
    pattern: "Schema-based validation"
    implementation: "Joi schemas"
    example: "userSchema.validate(userData)"
```

This isn't documentation for humans. It's a checklist for AI. Before generating code, the AI verifies: "Am I following established patterns?"

---

## Component 4: Cross-Session State

Track what was built and what's next.

```json
{
  "lastSession": "2024-12-18",
  "workCompleted": [
    {
      "component": "UserService",
      "status": "completed",
      "files": ["user.service.js", "user.repository.js"]
    }
  ],
  "workInProgress": [
    {
      "component": "OrderService",
      "status": "60% complete",
      "nextSteps": ["Add validation", "Implement error handling"]
    }
  ],
  "pendingDecisions": [
    {
      "decision": "Caching strategy",
      "options": ["Redis", "In-memory"],
      "context": "User lookup performance"
    }
  ]
}
```

New session starts. AI loads state. Knows OrderService is 60% done. Knows validation is next. Knows caching needs a decision before proceeding.

No confusion. No redundant work.

## The Validation Loop

Context preservation isn't just about storing information. It's about *validating against it*.

**Before generating code:**
1. Load ADRs and check for relevant decisions
2. Review naming conventions for the component type
3. Verify which patterns should be used
4. Check session state for context

**After generating code:**
1. Validate naming against conventions
2. Check pattern adherence
3. Flag any ADR violations
4. Update session state

**Example validation output:**

```
Validating code consistency...

Naming Convention Check:
✓ Class names follow PascalCase
✓ Function names follow camelCase
✗ API endpoint inconsistency: /users vs /api/orders

Pattern Adherence Check:
✓ Repository pattern used for data access
✗ Direct database query at order.service.js:45

Architectural Decision Check:
✓ JWT authentication per ADR-002
✗ Caching violates ADR-005 (Redis required)

ISSUES: 3 inconsistencies detected
```

The AI catches its own drift before it commits.

## Practical Implementation

### File Structure

```
your-project/
├── docs/
│   └── adr/
│       ├── 0001-repository-pattern.md
│       ├── 0002-jwt-authentication.md
│       └── template.md
└── .ai-context/
    ├── naming-conventions.yaml
    ├── established-patterns.yaml
    └── session-state.json
```

### Starting a Session

Include this in your prompt or system instructions:

```
Before starting work:
1. Read docs/adr/*.md for architectural decisions
2. Load .ai-context/naming-conventions.yaml
3. Check .ai-context/established-patterns.yaml
4. Review .ai-context/session-state.json

Validate all code against these sources.
Report any inconsistencies before proceeding.
```

### Ending a Session

Before finishing:

```
Update session state with:
- Work completed
- Work in progress (with percentage)
- Decisions made (create ADRs if significant)
- Next steps for following session
- Any pattern additions to established-patterns.yaml
```

## Common Objections

**"This is too much overhead"**

Initial setup takes an hour. After that, maintenance is minimal. And the hour you spend setting this up saves ten hours of fixing inconsistencies.

**"AI should just figure this out"**

AI operates session by session. It can't figure out what you decided last month without you telling it. Context preservation is how you tell it.

**"My codebase isn't that big"**

Context drift is worse in small codebases. In large ones, established patterns have momentum. In small ones, each session can swing in a different direction. Preservation matters more, not less.

---

## The Deeper Point

Context preservation isn't just about AI. It's about treating AI coding sessions as part of a continuous development process—not isolated events.

When humans join a project, they read docs, review existing code, ask about conventions. AI doesn't have onboarding. Context preservation is AI onboarding, every session, automatically.

The best AI collaborations don't just generate code. They generate *consistent* code. Code that fits. Code that follows the patterns. Code that makes the next developer (human or AI) understand what was built and why.

Context preservation makes that possible.
